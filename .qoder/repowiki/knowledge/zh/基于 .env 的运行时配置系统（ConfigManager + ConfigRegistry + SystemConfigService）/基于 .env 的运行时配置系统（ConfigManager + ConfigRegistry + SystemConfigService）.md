## 1. 使用的系统与框架

本仓库采用**自研的 `.env` 驱动的配置系统**，核心由三个模块组成：
- `src/core/config_manager.py`：`.env` 文件的原子读写、版本探测与变更合并。
- `src/config.py`：全局 `Config` dataclass 单例，负责从环境变量加载、类型解析、默认值与业务级校验。
- `src/core/config_registry.py`：配置字段元数据注册表（UI schema、分类、校验规则、敏感标记等），是 Web Settings 页面的唯一来源。
- `src/services/system_config_service.py`：面向 API/Web UI 的配置服务层，提供读取、验证、更新、导入/导出、LLM 通道测试、通知渠道测试、首次运行检查等功能。

持久化介质为项目根目录下的 `.env` 文件（可通过 `ENV_FILE` 环境变量覆盖路径）。启动时通过 `dotenv.load_dotenv` 将键值注入进程环境，后续所有模块通过 `os.getenv` / `Config` 访问。此外还支持通过 `LITELLM_CONFIG` 指向一个 LiteLLM 原生 YAML 路由配置文件，作为高级专家模式。

## 2. 关键文件与包

| 文件 | 职责 |
|---|---|
| `src/core/config_manager.py` | `.env` 行级解析、原子写入（先写 `.tmp` 再 `os.replace`，失败回退到原地重写）、敏感 key 掩码跳过、SHA256+mtime 版本字符串 |
| `src/config.py` | `setup_env()` 加载 `.env`；`Config` dataclass 定义全部配置项；`parse_env_int/float/bool` 等安全解析器；LLM 模型/温度/协议归一化逻辑 |

## 3. 架构与设计约定

### 3.1 配置加载顺序与优先级
1. 进程启动时调用 `src.config.setup_env(override=False)`，使用 `dotenv_values` 读取 `.env`（或 `ENV_FILE` 指定路径），不覆盖已存在的环境变量。
2. 运行时通过 `os.getenv` 获取值，再由 `Config` 字段上的解析函数做类型转换与边界钳制。
3. Web Settings 的“显示值”会合并进程环境中的 `LLM_*` 通道键（Docker `--env-file` 场景下 `.env` 未落盘但进程环境有值），保证设置页能展示启动注入的配置而不允许直接保存。
4. 高级用户可通过 `LITELLM_CONFIG` 指定 LiteLLM YAML 文件，其 `model_list` 优先于 channel/legacy 键生效。

### 3.2 原子写入与并发安全
`ConfigManager.apply_updates` 在 `threading.RLock` 保护下执行：
- 读取当前 `.env` 行 → 去重相同值 → 仅对变化的 key 生成新行 → 写入 `.env.tmp` → `os.fsync` → `os.replace` 原子替换。
- 当 `os.replace` 因挂载文件系统不支持（`EBUSY`/`EXDEV`）失败时，回退到原地重写并再次 `fsync`。
- 敏感 key 若传入值为 `mask_token`（如 `******`），则跳过写入，避免误清空。

### 3.3 配置字段元数据驱动
所有可编辑配置项必须在 `config_registry._FIELD_DEFINITIONS` 中注册，否则不会出现在 Web Settings 页面。字段元数据包含：
- 分类：`base` / `ai_model` / `data_source` / `notification` / `system` / `agent` / `backtest` / `uncategorized`
- UI 控件：`text` / `password` / `switch` / `textarea` / `select` / `number`
- 校验：`min/max`、`enum`、`multi_value`+`delimiter`、`item_type=url`+`allowed_schemes` 等
- 敏感标记：`is_sensitive=True` 的字段在 UI 中以密码框显示，服务端返回时可按需掩码
- 帮助链接：`help_key` 对应 i18n key，`docs` 数组携带外部文档链接

### 3.4 隐藏字段策略
`WEB_SETTINGS_HIDDEN_FROM_UI` 显式列出不可通过 Web 设置修改的键，包括数据库连接参数、代理、部分市场数据开关、以及所有加密货币交易凭据（`CRYPTO_TRADING_*`、`OKX_*`、`BYBIT_*`），这些仍支持通过环境变量或 `.env` 直接设置。

### 3.5 版本冲突控制
每次写入返回新的 `config_version`（`mtime_ns:sha256(content)`），导入/更新接口要求客户端传入当前版本，冲突时抛出 `ConfigConflictError`，防止并发覆盖。

### 3.6 LLM 配置三层模型
- **YAML 模式**：`LITELLM_CONFIG=./litellm_config.yaml`，最强大，支持完整 LiteLLM proxy 配置。
- **Channel 模式**：`LLM_CHANNELS=deepseek,gemini` + `LLM_DEEPSEEK_BASE_URL/KEYS/MODELS` 等前缀键，适合多模型编排。
- **Legacy 模式**：`OPENAI_API_KEY`、`GEMINI_API_KEY`、`ANTHROPIC_API_KEY` 等传统键，向后兼容。
三者按 YAML > Channel > Legacy 优先级解析，`channel_allows_empty_api_key` 对本地 `localhost/127.0.0.1` 或 `ollama` 协议允许空 key。

## 4. 约定与约束

- **所有运行时配置必须来自环境变量**：`Config` dataclass 字段默认值即为硬编码兜底，实际值一律经 `os.getenv` 读取。
- **新增可编辑配置项必须同时完成三件事**：在 `Config` 中添加字段、在 `config_registry._FIELD_DEFINITIONS` 注册元数据、在 `src/config.py` 的解析逻辑中处理默认值与校验。
- **敏感配置不得明文返回**：`LLM_USAGE_HMAC_SECRET` 在服务端响应中被强制掩码；其他 `is_sensitive=True` 字段由前端以 password 控件渲染。
- **Web 设置只允许修改 `.env` 中已注册的键**：未注册键会被忽略，未声明的键也不会出现在设置页。
- **`.env` 文件保持人类可读**：保留注释和空白行，仅更新发生变化的赋值行，末尾追加换行。
- **Docker 部署时 `.env` 可能不存在**：`SystemConfigService` 会从进程环境读取 `LLM_*` 通道键作为显示回退，但不允许保存回容器内文件。
- **通知渠道测试与 LLM 通道测试**：`SystemConfigService` 内置 `test_notification_channel` 与 `test_llm_channel`，分别验证目标渠道连通性与 LiteLLM 能力（json/tools/stream/vision）。
- **首次运行检查**：`get_setup_status` 统一检查 LLM、Agent、股票列表、通知、存储是否就绪，给出 `next_step_key` 引导用户补齐缺失配置。
- **Schema 版本**：`SCHEMA_VERSION = "2026-05-25"`，前端应据此判断兼容性。
