## 1. 整体方案

本仓库采用「`.env` 持久化 + Python `Config` dataclass 单例 + ConfigRegistry 元数据驱动」的三层配置体系：
- **持久层**：`src/core/config_manager.py` 中的 `ConfigManager` 负责 `.env` 文件的原子读写、版本哈希（`mtime_ns:sha256`）与敏感字段掩码。
- **运行时层**：`src/config.py` 中的 `Config` dataclass 通过 `setup_env()` 调用 `dotenv.load_dotenv`，把 `.env` 与环境变量合并为强类型对象，并提供 `parse_env_int/float/bool`、LLM 通道协议归一化等解析工具。
- **UI/校验层**：`src/core/config_registry.py` 维护每个环境变量的 schema（标题、分类、数据类型、默认值、验证规则、是否敏感、隐藏列表），由 `SystemConfigService` 暴露为 REST API，供 Web 设置页动态渲染表单。

启动时 `src/config.setup_env(override=False)` 优先保留进程环境变量，再加载 `.env`；更新后通过 `reload=True` 重新 `load_dotenv` 并重置 fetcher/search 单例，实现热重载。

## 2. 关键文件

| 文件 | 职责 |
|---|---|
| `src/core/config_manager.py` | `.env` 行级解析、原子 upsert（`os.replace` + errno 回退）、版本/更新时间计算 |
| `src/config.py` | `Config` dataclass（~300 个字段）、`setup_env`、LLM 通道协议/温度/模型归一化、新闻窗口/Agent 压缩预设 |
| `src/core/config_registry.py` | 字段元数据注册表（`_FIELD_DEFINITIONS`、`WEB_SETTINGS_HIDDEN_FROM_UI`、类别定义） |
| `src/services/system_config_service.py` | `SystemConfigService`：读取/校验/更新/导出/导入 `.env`，LLM 通道测试与模型发现，通知渠道测试，首次运行 setup 检查 |
| `api/v1/endpoints/system_config.py` | FastAPI 路由：`GET/PUT /config`、`/config/schema`、`/config/export`、`/config/import`、`/config/validate`、`/config/llm/test-channel`、`/config/notification/test-channel` |

## 3. 架构与设计决策

- **单一事实源**：所有可编辑配置项必须在 `config_registry.py` 中注册，否则不会出现在 Web UI 中。未注册的键仍可通过 `ENV_FILE` 注入到进程环境，但不会被 Settings 页面管理。
- **分层优先级**：进程环境变量 > `.env` 持久值；Web 设置写入仅修改 `.env`，不直接改内存；`get_config()` 会合并“运行时显示值”（来自进程 env）和“保存值”（来自 `.env`），用于展示当前生效值。
- **敏感字段保护**：`is_sensitive=true` 的字段在 UI 中以 password 控件呈现；`_SERVER_MASKED_CONFIG_KEYS`（如 `LLM_USAGE_HMAC_SECRET`）在服务端返回时强制替换为 `mask_token`，客户端需配合 `raw_value_exists`/`is_masked` 判断。
- **隐藏策略**：`WEB_SETTINGS_HIDDEN_FROM_UI` 显式排除数据库路径、代理、加密货币交易凭据、高级回测参数等，这些只能通过环境变量或部署脚本配置。
- **并发安全**：`ConfigManager.apply_updates` 使用 `threading.RLock` 串行化写操作；写入先落临时文件再 `os.replace`，遇到 `EBUSY/EXDEV` 回退到原地重写。
- **乐观锁**：每次更新/导入都携带 `config_version`，服务端用 `get_config_version()` 比较，冲突时返回 409 `config_version_conflict`。
- **LLM 多通道**：支持三种模式——① `LITELLM_MODEL` 单模型；② `LLM_CHANNELS` 逗号分隔的 channel 名 + `LLM_<NAME>_BASE_URL/API_KEY/MODELS` 系列键；③ `LITELLM_CONFIG` 指向标准 litellm `model_list` YAML（最高优先级）。频道协议通过 `resolve_llm_channel_protocol` 从 name/base_url/model 推断，本地地址默认走 `openai`。
- **通知渠道测试**：`test_notification_channel` 按 `_NOTIFICATION_TEST_TARGET_KEYS` 映射所需 key，校验必填组 `_NOTIFICATION_TEST_REQUIRED_KEY_GROUPS` 后真实发送一条测试消息。

## 4. 约定与约束

- **新增配置项必须三处同步**：`Config` dataclass 字段、`config_registry.py` 的 `_FIELD_DEFINITIONS`、必要时加入 `WEB_SETTINGS_HIDDEN_FROM_UI`。
- **`.env` 路径**：默认在项目根目录（`Path(__file__).parent.parent.parent / '.env'`），可通过 `ENV_FILE` 环境变量覆盖；`ConfigManager._resolve_env_path` 与 `setup_env` 两处保持一致。
- **布尔值解析**：统一通过 `parse_env_bool`，空串/`0/false/no/off` 视为 false。
- **数值边界**：`parse_env_int/float` 支持 minimum/maximum 钳制，越界时记录 warning 并回退到默认值。
- **LLM 温度优先级**：`LLM_TEMPERATURE` → 各 provider 专用温度 → 全局默认 0.7；provider 前缀通过 `_MANAGED_LITELLM_KEY_PROVIDERS` 与 `SUPPORTED_LLM_CHANNEL_PROTOCOLS` 白名单控制。
- **首次运行引导**：`get_setup_status()` 检查 LLM/Agent/股票列表/通知/存储五类必需配置，返回 `required_missing_keys` 与下一步提示。
- **备份/导入权限**：非桌面模式下 `/config/export` 与 `/config/import` 要求启用认证且携带有效 session cookie，防止未授权导出/覆盖 `.env`。
- **Schema 版本**：`SCHEMA_VERSION = "2026-05-25"`，前端据此判断是否需要迁移表单结构。

该体系将“静态常量 + 运行时环境变量 + 持久化 .env + UI 元数据”四层解耦，既支持运维通过环境变量注入密钥，又允许用户在 Web 设置页安全地调整非敏感配置，并通过 schema 驱动跨平台（Web/桌面/Bot）一致的设置体验。
